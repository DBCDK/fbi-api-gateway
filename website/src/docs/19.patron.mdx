# Patron

The `patron` root field provides the authenticated patron's profile, library
accounts, bookmarks, current loans, historical loans and consent for storing
historical loans.

Both queries and mutations require an authenticated Bearer token. The patron is
identified from the token, so no user ID or CPR number is supplied as an
argument. The Patron API is currently marked as `@draft` in the schema.

Pagination defaults to `offset: 0` and `limit: 10`. `limit` accepts values from
1 through 100.

## Basic patron information

The fields directly on `Patron` describe the account used for the current
login. Some profile fields are nullable because availability depends on the
login and the local library system.

## Library accounts

`accounts` contains at most one preferred account per agency. CPR-backed
accounts are preferred, with a local account used when the agency has no CPR
account. Account details are read live from the relevant library system.

Each account links to its library agency and all branches belonging to that
agency.

## Bookmarks

Bookmarks belong to the application configured for the calling client. The
optional `applications` argument filters the result by one or more
applications.

Bookmarks can be sorted by creation time or title:

The result contains both the stored snapshot and the currently resolved
material. Without a selection, a PID resolves `material.manifestation` and a
work ID resolves `material.work`. With a selection, `material.work` contains
the selected work and `material.manifestations` contains only manifestations
matching the selection. Bookmark snapshots use `materialTypes`; the former
singular `materialType` field is not part of Bookmarks V2. `materialTypes` is
present for manifestation bookmarks and bookmarks with a selection, and is
`null` for a bookmark of an entire work.

### Filter bookmarks

The optional `filter` accepts a work ID and returns every bookmark associated
with that work: bookmarks for the whole work, selections, and individual
manifestations.

A `hitcount` greater than zero means that the patron has bookmarked something
in the work. It does not necessarily mean that a particular PID is bookmarked.
To determine that, inspect `materialId` and `selection` on every matching item.
Clients must fetch pages until they have received `hitcount` items; using a
high `limit` alone does not guarantee that every item has been returned.

<InlineGraphiQL
  query={`
    query Example_FilterPatronBookmarks(
      $workId: String!
      $offset: Int
      $limit: PaginationLimitScalar
    ) {
      patron {
        bookmarks(
          filter: { workId: $workId }
          offset: $offset
          limit: $limit
        ) {
          hitcount
          status
          items {
            id
            materialId
            selection {
              materialTypes {
                general
                specific
              }
            }
          }
        }
      }
    }
  `}
  variables={{
    workId: "work-of:870970-basis:54029519",
    offset: 0,
    limit: 10,
  }}
/>

### Add bookmarks

`addBookmarks` accepts a PID or work ID with an optional material type
selection: either general or specific codes, all of which must match.
The API resolves the owning work and creates a snapshot; a PID with a
selection is stored as its work ID.

`agencyId` is set automatically from the agency in the URL, falling back to
the client configuration. Missing values are stored as `null`. Lists and add results
expose `agency` as the same `PatronAgency` type used by loans, or `null` if
unavailable. Read its ID through `agency { id }`.

Duplicates return `ALREADY_EXISTS` (counted as success) and keep their stored
agency, including `null`. Agency does not affect bookmark identity.
`dryRun: true` validates without saving. Dry-run, delete and unconfirmed error
results return `null` for `agency`.

## Current loans

Current loans are fetched live from OpenUserStatus. They can be filtered by
`ACTIVE` or `OVERDUE`, sorted by due date or title, and paginated. A loan is
considered overdue when its due date is before the current date in the

## Historical-loan consent

`isGranted` describes the stored consent, while `canBeChanged` indicates
whether the patron's age can be verified as at least 15 years.

Age verification primarily uses `birthDate` and `birthYear` from userinfo and
falls back to the CPR field. The CPR number itself is not exposed by the Patron
API or retained as part of this feature.

### Change historical-loan consent

The mutation result separates the operation status from the consent state.
`status: OK` means the operation completed, and `historicalLoanConsent` then
contains the resulting state.

Setting `consent` to `false` withdraws consent and permanently deletes all of
the patron's historical loans. Set `dryRun` to `true` to
validate and preview the resulting consent state without changing consent or
deleting data. The example below is a dry run.

<InlineGraphiQL
  query={`
    mutation Example_SetPatronHistoricalLoanConsent(
      $consent: Boolean!
      $dryRun: Boolean
    ) {
      patron {
        setHistoricalLoanConsent(consent: $consent, dryRun: $dryRun) {
          status
          historicalLoanConsent {
            isGranted
            canBeChanged
            status
          }
        }
      }
    }
  `}
  variables={{
    consent: false,
    dryRun: true,
  }}
/>

## Historical loans

Historical loans are only retained when historical-loan consent has been
granted. Results are paginated and returned in their default order.

If consent has not been granted, the collection has no items and returns
`CONSENT_REQUIRED`:

```json
{
  "hitcount": 0,
  "status": "CONSENT_REQUIRED",
  "items": []
}
```

Historical loans accept `filters: { applications, workId }`. Both fields are
optional and can be used independently. Applications
are combined with OR, and the work filter is combined with AND. Omit
`filters.applications` (or pass an empty list) for all applications; `[""]` matches none.
Filters apply before pagination; `hitcount` counts all matching loans, including
repeated loans of the same material and different materials belonging to a work.

Select `facets { name values { key score } }` to request application counts.
The API automatically requests facets from UserData only when the field is
selected, including through aliases and fragments. Fields excluded by `@skip`
or `@include` do not trigger facet calculation. No additional argument is needed.
`facets` is null when UserData omits it, including responses with `CONSENT_REQUIRED`.
Facets use dedicated `HistoricalLoanFacet` and `HistoricalLoanFacetValue` types
with the same structure as complex search. The application facet has
`name: "applications"`; each value has the application code in `key` and the
loan count in `score`. Historical loan facets have no `traceId` field. An available facet
with no matching applications is `[{ "name": "applications", "values": [] }]`.

Counts come directly from UserData, before pagination. They respect the user
and `filters.workId`, but ignore `filters.applications` so other applications remain
selectable. Loans with a null application are excluded from facet counts.
Counts represent individual loans and are independent of the returned page of
`items`; their sum can exceed the application-filtered `hitcount`.

`orderBy` defaults to `RETURNEDAT_DESC`. It also supports `RETURNEDAT_ASC`,
`TITLE_ASC`, `TITLE_DESC`, `CREATOR_ASC` and `CREATOR_DESC`. Missing values sort
last in both directions, with a stable secondary order. Return-date sorting uses
the timestamp when present, otherwise midnight in `Europe/Copenhagen`.
Work filtering and title/creator sorting of older records are only complete
after UserData backfill or reimport.

`application` is the application code associated with the historical loan,
mapped from UserData's `applicationName`, or null when unknown.

`loanedAtTimestamp` and `returnedAtTimestamp` are UTC timestamps or null.
The date fields remain calendar dates in `YYYY-MM-DD` format.
These capabilities require deployment of the updated UserData HistoricalLoans contract.

### Add historical loans

Manual historical-loan creation is intended for integration testing and can be
disabled by configuration. Consent is required before a loan can be stored.

`materialId` accepts a PID or a numeric faust number. Dates use `YYYY-MM-DD`,
and `returnedAt` cannot be earlier than `loanedAt`. Snapshot metadata is
resolved by the API and cannot be supplied by the client.

Optional `loanedAtTimestamp` and `returnedAtTimestamp` accept RFC 3339 strings
with an explicit timezone and at most three fractional second digits, for example
`2026-07-02T00:30:00+02:00`. The API derives the calendar date in
`Europe/Copenhagen`. If both date and timestamp are supplied for an event, their
Copenhagen dates must match; otherwise the API returns `BAD_USER_INPUT`.
Omitted or null timestamps leave date-only inputs unchanged.
Deduplication uses calendar dates, so different times on the same date do not
create distinct otherwise identical loans. Existing duplicates return
`ALREADY_EXISTS` without updating metadata.

When `dryRun` is true, identifiers, date ranges and material resolution are
validated without storing loans.

### Delete historical loans

Historical loans are deleted by their public IDs. Both manual and harvested loans
are deleted directly; repeating a deletion returns `NOT_FOUND`. Deletion does
not prevent later reimport of the loan. `dryRun` validates the IDs without deleting loans.

ADD and DELETE results expose nullable `agency` and `material { manifestation }`.
Agency information comes from the stored record returned by UserData and is
unavailable during dry runs. DELETE of an unknown ID has neither agency nor
material information. A manifestation can be null if the material no longer resolves.

<InlineGraphiQL
  query={`

## Status handling

Patron collection and mutation fields return status enums instead of throwing
for expected service and authentication outcomes. Input validation errors,
such as a negative offset or an empty mutation batch, are returned as GraphQL
errors with the code `BAD_USER_INPUT`.

Clients should inspect both the collection or operation status and individual
item statuses. For batch mutations, `PARTIALLY_FAILED` means at least one item
succeeded and at least one item failed.
